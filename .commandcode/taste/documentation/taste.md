# Documentation

- For system-design concept docs, wants every topic covered with the same recipe: detailed explanation, real-life use case, interview questions with answers, diagrams (mermaid), and Java/Spring Boot code examples. Confidence: 0.95
- Wants concept docs organized with a "Topics Covered" numbered list (with anchor links to every subsection, listed first under a `## Theory` section progressing fundamentals → advanced), followed by the canonical ordered sections (24 canonical topics total): Introduction/Problem Statement, Characteristics, Pros, Cons, Use Cases, Components, Architectural Patterns, Benefits, Challenges, Best Practices, When to Use / When Not to Use, Data Model and API, [domain-specific technical sections], then the security/infra sections (Encryption and Key Management, Authentication and Authorization, Replication Strategies, Failure Detection and Membership, High Availability and Scalability, Performance and Optimization, CAP Theorem and Consistency Trade-offs, Security Threats and Mitigations, Observability and Logging), Real-World Implementations, Java and Spring Boot Implementation Guide, and Interview Questions and Answers — with a detailed explanation for each individual point, not just one-liners. Confidence: 0.95
- When editing existing docs, never remove existing content — review, correct, and elaborate it instead. Confidence: 0.95
- Interview-prep sections should target senior Java backend / system-design interviews: grade questions from beginner to senior/system-design level, answer each in depth, and add likely follow-ups, expected discussion points, common mistakes, and trade-offs. Each file includes BOTH inline interview Q&As within each section AND a dedicated `### Interview Questions and Answers` section at the end. Confidence: 0.9
- Relevance gate: only add sections that fit the specific topic (API contracts for API topics, data modeling for storage topics, distributed considerations for distributed topics); never force template sections or Spring Boot examples into topics where they don't belong. Confidence: 0.95
- Avoid duplicating shared concepts between related topic files — give a concise explanation and cross-reference the relevant topic instead. Confidence: 0.9
- Keep headings, terminology, formatting, diagram style, code style, and explanation depth consistent across all topic files. Confidence: 0.9
- Diagrams: prefer Mermaid, pick the right diagram type per concept (flowchart, sequence, class, ER, state, architecture, data-flow), keep them syntactically valid, and accompany every diagram with a clear explanation of what it shows and how to interpret it. Confidence: 0.85
- Finished docs must contain no placeholders (`TODO`, `TBD`, incomplete sections); close out with a review pass verifying consistency, balanced Mermaid fence counts, diagram syntax correctness, and code correctness. Verify TBD/TODO using **word-boundary regex** (`\btbd|todo\b`), not loose substring matching — loose matching produces false positives from words like "toDocument" or "Mastodon" that contain "todo" as a substring. Confidence: 0.82
- Unbalanced Mermaid fence diagnosis: a file with an odd fence count (`grep -c '```'` is odd) typically has a single stray ``` at the very end of the file (after the last content section) that opens an unclosed code block, rather than a missing closing fence somewhere in the middle. Fix by removing the stray trailing triple-backtick or adding the missing one. Confidence: 0.75
- Checkpoint files (`todo.md`) mirror across parallel directory structures (e.g., the `basic` and `advanced` directories each have their own `todo.md`) to track progress, document the canonical template, and reference a gold-standard file for resuming work. The todo.md must reflect the **actual current state** of every file (line counts, Topics Covered / Java / Interview presence, fence balance, TBD-free status, and per-file missing canonical topic count with specific list), not aspirational targets, so that the next LLM run can understand exactly what to do. Confidence: 0.92
- Bidirectional topic parity: when comparing two paired reference files (e.g., basic/vpn.md and advanced/key-value-store.md), the user wants topics added in **both directions** — enhance file A with file B's missing relevant topics, then enhance file B with file A's missing relevant topics — ensuring the pair shares the same topic set. Domain-specific topics that don't apply (e.g., Tunneling doesn't apply to key-value stores) are correctly skipped. Confidence: 0.9
- Audit-driven workflow: the user accepts and the workflow uses Python audit scripts that scan all `.md` files in a directory, extract `### Topics Covered` numbered lists and `###` section headings, then use normalized keyword matching (lowercase, hyphens→spaces) to determine which of the 24 canonical topics are present or missing per file. The results (line count, missing topics, fence count, TBD presence) feed directly into the todo.md status table so the next LLM run knows exactly what to do. Confidence: 0.82
- Topics Covered numbered items include anchor links (`[title](#anchor-slug)`) to their corresponding `###` subsections — including all domain-specific technical sections (Encryption, Auth, Replication, etc.), not just the reference sections — for jump navigation, and the review pass verifies every Topics Covered entry resolves to an existing subsection. Confidence: 0.85
- Audit verification checks for **exact canonical heading strings** (`### Java and Spring Boot Implementation Guide`, `### Interview Questions and Answers`, etc.) as quality gates — a section whose content exists but is under the wrong heading level (e.g., `##` instead of `###`) fails the canonical topic check and must be corrected. Heading-level consistency is a hard requirement, not just content presence. Confidence: 0.75
- When audit grep flags potential TBD/TODO matches, inspect the actual match context (e.g., `grep -in` output with surrounding lines) and apply domain-specific knowledge (track IDs in music docs, method names like `mapToDouble`/`toDocument` containing "todo" as a substring) to classify false positives before treating them as real placeholders. Word-boundary regex is the first filter, but context inspection catches edge cases regex alone may miss. Confidence: 0.75
- After restructuring a file from the old `### Important Subtopics` format into the canonical template, **remove the leftover `### Important Subtopics` heading** from completed files rather than leaving it alongside the new canonical sections — the old-format heading is a structural artifact, not content to preserve. Completed files should contain only canonical headings. Confidence: 0.7
